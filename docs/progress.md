# 개발 진행 기록

## 2026-10-27 — 0.4.0 데이터 기반 콘텐츠

아이템별 코드 분기를 제거하고 `CSV/JSON → ContentLoader → ItemData/EffectUnit → EffectApplier` 흐름으로 전환했다. 기존 아이템 12종·적 3종·수치·배치를 유지하며, 조합 가능한 효과와 Google Sheets 가져오기용 밸런싱 템플릿을 제공한다. 사용 절차와 효과 계약은 [데이터 파이프라인](data-pipeline.md)에 있다.

- `ItemData`, `EffectUnit`은 필드만 가진 Resource다. 회전·스냅샷 변환·효과 계산·UI 표현은 각각 별도 계층이 소유한다. 런타임에서 특정 아이템 ID나 태그를 조건으로 쓰지 않는다.
- 효과는 발동 시점·연산·대상·인접 태그·횟수·중첩 그룹·우선순위로 조립한다. 비용은 사용 요청당 한 번 지불한다. 적 의도와 반응, 런 기본 수치와 초기 지급도 데이터로 옮겼다.
- CSV와 JSON은 동일 스키마·참조 검사를 거친다. 실패한 가져오기는 기존 파일을 보존하고, 게임 재시작의 로드 실패도 기존 세션을 보존한다. 실행 중 전투에 새 콘텐츠를 섞지 않는다.
- 판정 복사본·FIFO·원인 ID·단일 커밋과 기존 Action Queue를 유지한다. 장착·보관·소모 상태에 따라 반응 출처를 수집하며, 효과 계획과 연쇄 모두 상한을 둔다.
- UI 설명·대상·효과 수치는 데이터와 공통 계산으로 만들고, 긴 복합 효과 카드는 스크롤한다. 아이콘·캐릭터의 기존 픽셀 사각형도 데이터로 이관했다.
- 회귀 테스트는 고정 `tests/fixtures/baseline.json`을 사용한다. 출시 수치 조정과 규칙 회귀 검증을 분리했다. 반사·반응 방어·추가 500개 정의는 테스트 전용이며 출시 콘텐츠를 늘리지 않았다.

검증: `bash scripts/export-windows.sh`에서 필수 `bash scripts/check.sh` 전체 실행. 콘텐츠 **53개**, 기존 규칙 **99개**, 연쇄 **22개**, 재생 **24개**, 총 **198개 실패 0**. 구조 경계, UI 통합, 잘못된 입력의 기존 JSON 보존, 실제 release PCK의 데이터·메인 장면 로드도 통과했다. PCK 검사는 소스가 없는 작업 폴더에서 실행하고 테스트 픽스처가 패키지에 들어가지 않은 것도 확인한다. 0값 방어 설정의 턴 종료·피해 반응과 복합 효과의 FIFO 순서를 포함한다.

템플릿은 7개 탭과 2000행 참조·입력 검증 범위를 제공한다. 배율 1→2에서 공격 6→12·수정 효과 2→4, 새 행의 원수치 7→14, 원상 복구를 확인했다. 계산 결과 CSV를 실제 Godot 로더의 `--check`로 검증하고 전체 탭 렌더링을 확인했다. Google 계정 업로드·원격 Sheet 생성·Google Sheets 자체 재계산은 수행하지 않았다.

macOS 0.4.0 실행 로그에는 오류가 없지만, UI 도구가 별도 프로젝트 매니저를 선택해 이번 버전의 실제 마우스 조작 검증은 완료하지 못했다. 자동 UI 검사는 3개 해상도, 드래그·직접 사용·표시 시점·긴 설명 스크롤을 통과했다. Windows 실기기 실행과 외부 플레이 관찰은 여전히 별도다.

전달 파일: `outputs/data-driven-content/balance-template.xlsx`, `build/JeoseungBundle-prototype-0.4.0-windows.zip`, `build/source-snapshot-0.4.0-2026-10-27.zip`. 기존 효과 어휘 안의 새 조합은 데이터만으로 만들 수 있다. 독 지속 시간·소환처럼 새로운 연산은 스키마·엔진·검증 확장이 필요하다.

## 2026-10-27 — 0.3.0 보따리 중심 UI

사용자가 제공한 Backpack Hero 화면을 기준으로 기존 3열 패널을 상단 보따리·하단 전투 무대·우측 턴 종료 구도로 교체했다. [UI 구성](ui-layout.md)에 참고 이미지와 조작·표현 규칙을 기록했다.

- 보따리 물건을 전투 중 클릭하면 바로 사용한다. 호버 카드로 현재 효과·기력 비용·인접 원인·사용 가능 여부를 확인한다.
- 준비·승리 단계에서 보관대 → 보따리 드래그를 지원한다. 전투 중에는 정리 도구를 숨기고 배치를 잠근다.
- 물건의 글자 표현을 공통 팔레트·24px/칸 단위의 코드 픽셀 아이콘으로 교체했다. 기존 12종과 적 3종, 칸 수·규칙은 그대로다. 원본 게임의 이미지 자원은 사용하지 않았다.
- `BattleLayout`이 화면 배치와 배경, `ItemIcons`가 공통 표현, `Main`이 입력 연결·표시 상태를 맡는다. Simulation/Playback과 Action Queue 구조는 유지한다.
- 긴 설명의 중복 기본 수치와 체력바·숫자 겹침을 정리했다.

검증: `bash scripts/export-windows.sh` 안에서 `bash scripts/check.sh` 전체 실행. 구조 경계, 기존 규칙 99개, 연쇄 22개, 재생 24개, UI 통합 검사 모두 통과했다. UI는 보관대 드래그·직접 사용·연속 클릭 잠금·약과 표시 시점과 1024×576/1280×720/1920×1080의 설명 창 경계·턴 버튼 비가림, 축소 시 드래그를 확인한다. macOS 실제 창에서는 부적 드래그 후 검 6→8, 검 직접 클릭 후 피해 8·기력 1 소모, 보관대 약과 드래그, 한글 표시와 최종 체력바 배치를 확인했다. 해상도별 자동 레이아웃 검사는 OS 디스플레이 배율 수동 검증을 대신하지 않는다.

전달 파일: `build/JeoseungBundle-prototype-0.3.0-windows.zip`, `build/source-snapshot-0.3.0-2026-10-27.zip`. 이전 ZIP은 유지한다. Windows 실기기 실행과 외부 관찰은 여전히 미검증이며, 최종 픽셀 에셋·애니메이션은 후속 단계다.

## 2026-10-27 — 0.2.0 판정·재생 분리

전투 입력은 `BattleSession.submit()`으로 모으고, 순수 판정 → 성공 결과의 단일 커밋 → Action Queue 재생으로 분리했다. 구현과 macOS 조작 확인은 10월 26일에 진행했으며, 중단 이후 27일에 결과와 전달 파일을 정리했다. 자세한 계약과 확장 규칙은 [전투 아키텍처](combat-architecture.md)에 있다.

- 판정기는 값 스냅샷에서 인접 보너스·타격·반응·소모·승패까지 계산하고 원인 ID와 단계별 상태를 기록한다.
- 화면은 `display_snapshot()`만 읽는다. 실제 소모된 물건도 소비 이벤트가 재생되기 전까지 표시 상태에 남아 체력·기력·보드가 서로 다른 시점을 섞지 않는다.
- 큐는 프레임마다 명령 하나를 시작하며 완료 신호를 먼저 연결한다. 중복 완료, 늦은 완료, 재진입, 재시작, 장면 종료를 처리한다.
- 재생 중 중복 입력과 배치를 잠근다. 건너뛰기·완료 시간 초과는 이미 확정한 상태로 화면을 맞추며 판정을 반복하지 않는다.
- 연쇄 효과 수·이벤트 수 128, 깊이 32, 트리거별 행동당 횟수 제한을 적용한다. 한도 초과는 비용을 포함한 전체 행동 거절이며, 치명타 반응까지 처리한 뒤 승패를 확정한다.
- `AGENTS.md`와 구조 경계 검사를 추가해 후속 작업에서 UI·연출에 판정과 await가 섞이는 실수를 감지한다.

검증: 기존 규칙 **99개**, 연쇄 판정 **22개**, 재생·취소 **24개**, 총 **145개 실패 0**. 구조 경계 검사와 UI 통합 검사도 통과했다. UI 검사는 약과의 실제 소모와 화면 제거 시점, 재생 전후 체력바, 입력 잠금, 컨트롤 경계를 포함한다. macOS 실행 창에서는 공격 연속 클릭 후 피해·기력이 한 번만 적용되는 것과 턴 종료 후 건너뛰기의 최종 상태를 확인했다.

가시 반사와 반응 방패는 테스트 픽스처로 검증했다. 기존 아이템 12종·적 3종의 콘텐츠 수와 능력은 유지한다. 새 반응을 실제 장비에 연결하는 콘텐츠 작업, 저장, Windows 실기기 검증은 별도다.

전달 파일: `build/JeoseungBundle-prototype-0.2.0-windows.zip`, `build/source-snapshot-0.2.0-2026-10-27.zip`. Windows 패키지는 교차 내보내기 결과이며 실제 Windows 실행을 확인한 것은 아니다. 아래 0.1.0 기록과 이전 ZIP은 비교·복구용으로 유지한다.

## 2026-10-26 — 0.1.0 규칙 프로토타입

개발 플랜의 M0 → M1 → M2 순서로 첫 플레이 가능한 버전을 만들었다. 사용자 파트타임 공수를 소비했다고 계산하지 않는다. 에이전트 작업은 약 15:10 KST에 시작했으며 설계·구현·다운로드·승인 대기·검증을 포함한다. 최종 검증·패키지 기록 시점은 2026-10-26 16:28 KST이다. 세부 작업별 순수 제작 시간은 측정하지 않아 기존의 54~82시간 추정을 이번 세션 경과 시간으로 대체하지 않는다.

| 단계 | 현재 상태 | 남은 완료 조건 |
|---|---|---|
| M0 제작 기반 | Godot 4.7.2·템플릿 고정, Git 초기화, 로컬 스냅샷, 검사·빌드 스크립트, Windows ZIP | Windows 실기기 실행·환경 기록. 커밋·원격 백업 별도 |
| M1 인벤토리 | 기본 범위 구현·내부 검증 | Windows 조작 확인, 외부 관찰에 따른 수정 |
| M2 전투 | 3전투·두 배치 완주 내부 검증 | 외부인 3~5명 규칙 이해·선택 이유 관찰 |
| M3 이후 | 계획 유지 | M2 결과 확인 후 기준 시트와 아트 제작시간 측정 |

## 구현

- 5×4 보따리, 인스턴스 ID와 공유 Resource 분리, 직사각형·L자 포함 아이템 12종.
- 클릭 배치·보따리 내 드래그·90° 회전·취소·임시 보관대·배치 되돌리기 30회.
- 경계·겹침 거절, 전투 중 배치 잠금, 무효 배치·취소 시 확정 상태 보존.
- 상하좌우 인접, 같은 상대 중복 제외, 동일 부적 중복 제외, 혼백등의 유품 2개 상한.
- 부적→무기 공격 증가, 혼백등→유품 방어, 등 옆 동경의 방어 보너스.
- 미리보기·상세 정보·실제 전투가 같은 규칙 계산 사용.
- 기력 3, 턴당 아이템 1회, 공격·방어·회복, 일회용 약과, 사용 상태 표시.
- 의도를 표시하는 적 3종, 승리·패배·재시작, 승리 시 최대 체력 4 회복, 전투 사이 정리.
- 한국어 UI와 Noto Sans KR, 먹남색·한지색·청록·금빛의 공통 임시 표현.

그림은 규칙 확인용 도형이다. 최종 픽셀 에셋·애니메이션·음향은 아직 제작하지 않았다. 보상 선택, 경로, 임무 유품 잠금, 저장/이어하기, 난수, 사연, 해금, Steam 연동, 모바일도 현재 구현에 포함되지 않는다. 현재 게임은 매번 같은 초기 상태로 시작한다.

|---|---|
| Godot 가져오기·스크립트 파싱 | 통과 |
| 규칙 자동 검사 | **99개, 실패 0** |

| 서로 다른 배치의 3전투 완주 | 방어 배치·공격 배치 모두 생존·완주. 밸런스/재미 검증은 아님 |

| 1080p·최소 창·배율·장시간 플레이 | 별도 수동 검증 필요 |
| 외부 플레이어 관찰 | 미실시 |

재현 절차는 [프로토타입 테스트](prototype-playtest.md)에 있다. 자동 검사 성공을 M2 재미 검증 또는 Steam 출시 준비 완료로 취급하지 않는다. 실행·검사·내보내기 로그는 `build/logs/`에 남긴다.

## 발견하고 수정한 문제

1. `Control.rotation`과 아이템 회전 변수의 이름 충돌: 아이템 미리보기는 `pending_rotation`으로 분리했다.
2. 드래그에서 OS 포인터에 의존해 입력 이벤트와 좌표가 어긋나는 문제: 이벤트 좌표와 캔버스 변환을 사용하고 회귀 검사를 추가했다. 실제 창에서 재확인했다.
3. 부적 이동 미리보기가 선택한 부적만 계산하던 문제: 영향을 받는 검 공격과 가호 변화도 표시한다.
4. 모든 물건을 보관대로 옮겼을 때 공간이 늘어나는 문제: 보관대를 스크롤 영역으로 고정했다.
5. 가변 글꼴이 너무 가늘게 표시되는 문제: OpenType weight 축을 정수 태그로 지정하고 실제 화면에서 굵기를 확인했다. [Godot FontVariation 문서](https://docs.godotengine.org/en/stable/classes/class_fontvariation.html)
6. 마지막 전투 뒤 안내가 다음 길목을 가리키던 문제: 연습 완료 메시지로 수정했다.
7. release에서 `assert` 안의 초기화가 생략될 위험: 아이템 추가를 먼저 실행하고 결과만 검증한다.
