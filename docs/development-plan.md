# 저승 보따리 — Steam 선출시 개발 플랜

작성: 2026-10-26 · 진행 갱신: 2026-10-29 · 상태: **0.14.0 아랑전설 1스테이지·정적 픽셀풍 시안 적용, Windows 실행·M2 외부 관찰 대기**

확정 조건: **1인 파트타임 개발**, Godot, 한국 저승사자 소재의 인벤토리 퍼즐 로그라이트, 2D 픽셀 아트의 일관성, Steam 선출시 후 반응을 보고 모바일 배포 판단.

이 문서는 작업 순서·범위·공수·완료 기준을 관리한다. 게임 규칙과 아트 규격은 [게임 설계](game-design-v0.1.md)를 따른다. 아래 콘텐츠 수량과 시간은 제작 제안이며, 프로토타입과 아트 샘플의 실제 작업시간을 확인한 뒤 갱신한다.

현재 구현·검증 근거와 다음 작업은 [진행 기록](progress.md)에 기록한다. 공간적 기회비용·연쇄 시너지·적 의도·연출의 후속 실험은 [공간 딜레마와 연쇄 시너지](space-synergy-proposal.md)에 정리한다. 1×4 테스트 무기는 [별도 실험 모드](space-experiment.md)에서 검증하며 플레이어 관찰은 아직 남았다. M1 기본 기능과 M2 내부 전투 루프를 구현했지만 M0의 Windows 실기기 실행, M2의 외부인 3~5명 관찰은 아직 통과하지 않았다. M3 중 기존 정적 캐릭터의 전투 피드백, M4 중 전투 보상·재배치·로컬 저장·두 경로 선택·첫 사연 기록·첫 유품 사건, M5 중 단계별 길잡이, M8 중 아이템 데이터·검증 도구를 선행 구현했다. 길잡이는 외부인이 도움 없이 이해하는지 검증해야 하므로 M5 완료가 아니다. M4의 추가 사건·장터·난수 진행 및 Windows 저장 검증과 M8의 지역·사연 템플릿·개발용 시드 선택은 남아 있다. M3~M11의 나머지 범위는 아래 계획을 유지한다.

추가로 [턴 종료 미리보기](turn-preview.md)와 [민화·목판화 아트 방향 시안](art-direction.md)을 만들었다. 시안은 제작용 개별 스프라이트가 아니며 M3의 기준 에셋 제작·승인과 외부 관찰은 계속 남는다.

대각선과 상하좌우·대각선 합집합을 데이터 기반 범위로 지원하며 [대각선 실험 모드](diagonal-experiment.md)를 제공한다. 출시 콘텐츠에는 새 범위를 적용하지 않았다. 플레이 관찰과 최종 아트는 별도다.

정수 배율도 데이터 기반으로 추가하고 [배율 실험 모드](multiplier-experiment.md)에서 계산 근거를 표시한다. 출시 콘텐츠에 배율을 적용하거나 외부 플레이를 관찰하지는 않았다. 분수 배율과 유한 자동 연쇄는 별도다.

[시너지 연결 표시](synergy-visualization.md)는 확정 배치와 가상 배치의 출처·대상·범위·조건을 화면에 구분해 표시한다. 외부 플레이어의 이해도와 펄스 연출은 아직 검증·구현하지 않았다.

## 1. 일정의 전제

- 가용 시간은 **주 10시간**으로 임시 산정한다. 사용자가 확정한 것은 파트타임이며 실제 주간 시간은 아직 미정이다.
- 프로그래밍·기획·픽셀 아트·사운드 편집·QA·배포를 한 사람이 순서대로 수행한다. 별도 아티스트가 동시에 작업한다고 계산하지 않는다.
- Godot 기초 사용과 작은 2D 프로젝트 수정이 가능한 경우를 가정한다. 엔진·픽셀 아트를 처음부터 배우는 시간, 장기 휴식, 외주 대기는 별도다.
- 계획 수립 당시에는 문서만 있었다. 현재 `game/project.godot`, 규칙·UI·아이템 12개·전투 프로토타입과 검사·빌드 스크립트가 있다.
- 첫 출시 대상은 Windows를 제안한다. Mac에서 개발하더라도 M0부터 Windows 실기기 테스트 경로를 마련한다.
- 기본 공수에 일반적인 수정·검증·문서화를 포함하고, 예상 밖 재작업을 위해 **25% 여유**를 추가한다.
- 공수는 업계 평균이나 출시 약속이 아니다. 첫 20시간과 M3 종료 시 다시 산정한다. 대외 출시일은 아직 정하지 않는다.

| 목표 | 기본 공수 | 25% 여유 포함 | 주 10시간 기준 |
|---|---:|---:|---:|
| 전투 가능한 임시 그래픽 프로토타입, M0~M2 | 54~82시간 | 약 68~103시간 | 약 7~11주 |
| Steam 공개 데모, M0~M6 누적 | 200~296시간 | 약 250~370시간 | 약 25~37주 |
| 데모 이후 정식 출시, M7~M11 추가 | 320~480시간 | 약 400~600시간 | 추가 40~60주 |
| Steam 정식 출시, 시작부터 누적 | 520~776시간 | 약 650~970시간 | 약 65~97주 |

주 10시간을 지속하면 공개 데모는 약 6~9개월, 정식 출시는 시작부터 약 15~23개월을 계획 범위로 본다. 아트 숙련도와 실측 생산량에 따라 차이가 크다.

| 실제 주간 작업시간 | 공개 데모 | 정식 출시 누적 |
|---|---:|---:|
| 5시간 | 약 50~74주 | 약 130~194주 |
| 10시간 | 약 25~37주 | 약 65~97주 |
| 15시간 | 약 17~25주 | 약 44~65주 |

위 표는 여유를 포함한 작업시간을 주당 시간으로 나눈 값이다. 외부 심사·테스터 모집처럼 다른 작업과 겹치지 못하는 대기 시간은 추가된다. 주간 시간을 늘려도 이런 대기까지 비례해서 줄어들지는 않는다.

## 2. 제작 범위

| 항목 | 규칙 프로토타입 | Steam 공개 데모 | 정식 1.0 제안 |
|---|---|---|---|
| 주인공 | 임시 표현 1명 | 1명 | 1명, 시작 장비 구성 3종 |
| 아이템 정의 | 12개 | 16개 | 40개 |
| 일반 적 | 3종 | 4종 | 10종 |
| 보스 | 없음 | 1종 | 2종 |
| 지역 | 테스트 배경 | 1개 | 2개 |
| 사건 | 없음 | 3개 | 10개 |
| 망자 사연 | 규칙 확인용 | 완결 사연 1개 | 완결 사연 3개 |
| 주요 빌드 계열 | 2개 | 2개 | 3개 |
| 플레이 흐름 | 짧은 연속 전투 | 한 구역, 10~15분 출장 | 두 구역, 20~30분 출장 목표 |
| 그래픽 | 정적 픽셀 시안 | 공통 규격의 최종 품질 에셋 | 같은 규격으로 확장 |

정식판 수량은 **데모 포함 누적치**다. 아이템은 데모 이후 24개를 추가한다. 단순 능력치·색상 변형을 별개 행동 패턴이나 효과로 세지 않는다. 정식판은 한 인도 사건의 시작과 결말, 반복 플레이 가능한 해금 구조를 갖춘다.

기존 구상의 데모 아이템 24개·일반 적 6종·사건 6개와 본편 3구역은 확장 후보로 이동한다. M3의 에셋 생산 속도와 M6의 데모 반응을 보고 재검토한다.

전투 사이 재배치와 전투 중 기력 사용을 기본 규칙으로 둔다. 전투 중 재배치·복잡한 저주·다수 직업·마을 건설·제작·실시간 전투·온라인 기능은 현재 범위에 포함하지 않는다. 모바일 UI, Mac/Linux 출시, 컨트롤러/Steam Deck, 추가 지역도 별도 결정과 공수 산정이 필요하다.

## 4. 단계별 계속 진행할 기준

**M2 — 배치의 재미:** 외부인 3~5명에게 같은 아이템으로 전투하게 한다. 소규모 관찰은 통계적 시장 검증이 아니라 반복되는 불편을 찾기 위한 것이다. “왜 이 물건을 옮겼는가?”를 설명할 수 있는지, 정답 하나만 반복되는지, 전투 후 장비를 바꿀 이유가 있는지 기록한다. 공간 선택에 의미가 없으면 콘텐츠 생산 전에 규칙을 수정한다.

**M3 — 아트 생산 가능성:** 아이콘 6개와 캐릭터 샘플의 제작·수정·출력·게임 적용 시간을 기록한다. 실측 단가와 남은 수량으로 M5·M9를 재산정한다. 초과하면 애니메이션 종류·장식·새 실루엣 수를 줄인다. 공통 팔레트·픽셀 밀도·핵심 판독성은 유지한다.

**M6 — 본편 확대 근거:** 초대 테스트 10~20명을 첫 목표로 잡는다. 데모 완주, 막힌 위치, 스스로 재도전했는지, 유품 선택을 기억하는지와 정리 피로를 관찰한다. 조작 문제를 해결했고 두 빌드와 유품의 가치를 경험하는지 확인한 뒤 본편을 늘린다. 모집이 부족하면 결과를 확정하지 않는다. 위시리스트 한 지표로 통과시키지 않는다.

추가 기본 공수는 320~480시간, 여유 포함 400~600시간이다. 에셋 실측 단가가 높으면 수량이나 일정을 다시 정한다. 세 번째 지역은 이 계획을 완수하기 위한 필수 항목이 아니다.

Steam Cloud와 도전과제는 M7에서 도입 범위를 결정하고, 채택한 기능의 구현·오프라인·복귀·동기화 검증을 M11에 배정한다. 연동 범위를 늘리면 다른 범위나 시간을 조정한다. 핵심 게임은 로컬 저장으로 독립 실행 가능하게 만든다.

## 6. 첫 20시간 체크리스트

- [ ] **DEV-002 / 3시간:** 1280×720, 입력 액션, Windows x86_64 preset·EXE·ZIP 구현. **Windows 실기기 실행 증거가 없어 미완료**.

## 7. Godot 구현 순서

```text
game/
  project.godot
  scenes/       관청, 지도, 전투, 보상 화면
  scripts/
    core/       인벤토리 규칙, 전투 계산, 런 상태
    ui/         입력 처리와 표시
    services/   저장, 플랫폼 연결
  data/         아이템, 적, 사건, 사연 Resource
  assets/       게임용 이미지·음향·글꼴
  tests/        규칙·저장 회귀 검증
art-source/     픽셀 원본, 팔레트, 승인 기준 시트
docs/           기획, 개발 플랜, 테스트 기록
```

폴더는 기능을 구현할 때 만든다. 의존 순서는 `점유·회전 → 인접 효과 → 미리보기 → 전투 → 보상·경로 → 저장 → 유품 사건 → 콘텐츠 확대 → Steam 배포`다.

- 공유 아이템 정의와 런타임 좌표·사용 횟수를 분리한다.
- UI는 선택·배치·사용 명령을 전달하고 규칙 코드는 상태를 계산한다.
- 효과 미리보기와 실제 전투는 같은 계산 경로를 사용한다.
- 결과 상태와 애니메이션을 분리하고 확정 상태를 저장한다. 현재 [전투 아키텍처](combat-architecture.md)의 순수 Simulation → 원자적 커밋 → Action Queue Playback을 적용했다. 영구 저장은 M4에서 이어간다.
- 콘텐츠 ID, 저장 버전, 난수 시드·생성기 상태를 기록한다. 번역·아트 교체로 ID가 바뀌지 않게 한다.
- 모바일에 대비해서 입력·규칙·표시의 경계만 유지하고, 현재 화면은 PC에 집중한다.

## 8. 에셋 제작 계획

M0~M2는 도형과 텍스트로 검증한다. M3에서 주인공·적 1종·아이템 6개·배경 조각·보따리를 같은 화면에 만든다. 팔레트·외곽선·광원·캔버스·비율·애니메이션 기준점을 아트 바이블로 고정한 뒤 M4~M5에서 4~6개씩 추가한다.

M3의 기존 작업 범위에 [저승사자 참고 노트](lore-reference.md)의 복식·소지품 확인을 포함한다. 갓·먹빛 겉옷·문서·보따리의 실루엣을 우선 검토하고, 데모 16개 안에서 적패지·오라·짚신·사잣밥 소재의 활용을 검토한다. 출전의 지역과 게임 창작을 구분하며, 새 시스템·아이템 수·등장인물을 자동으로 추가하지 않는다.

| 데모 에셋 | 수량 가설 | 제작 제한 |
|---|---:|---|
| 주인공 | 1명 | 대기·행동·피격 중심. 화면에 필요하지 않은 걷기·다방향 애니메이션 제외 |
| 일반 적 | 4종 | 서로 다른 실루엣. 대기·공격·피격 중심, M3 샘플 포함 |
| 보스 | 1종 | 핵심 행동·위험 예고 우선, 장편 컷신 제외 |
| 아이템 아이콘 | 16개 | 기준 시트 6개 포함. 다칸도 같은 픽셀 밀도 |
| 전투 배경 | 1세트 | 정적 레이어와 소수 분위기 효과 |
| 지도·관청·장터 | 공통 UI 기반 | 별도 탐험 맵 대신 메뉴·배경·소품 활용 |
| 대화 인물 | 3명 내외 | 초상 또는 작은 스프라이트로 통일, 주인공 표현 재사용 |
| 효과 | 4~6개 | 공격·방어·회복·봉인·보상을 여러 아이템이 공유 |
| UI | 공통 1세트 | 슬롯·버튼·패널·아이콘·커서 상태 |
| 사운드 | 효과음 10~15개, 음악 2곡 내외 | 직접 편집 또는 이용 조건을 확인한 라이선스 자원 |
| 상점 | 로고·캡슐·스크린샷·짧은 영상 | 실제 빌드와 공통 아트 기준 적용 |

사운드 공수는 기존 라이선스 자원의 선택·편집·통합을 기본으로 한다. 전곡 작곡이나 외주를 선택하면 비용·납기를 다시 잡는다. 생성형 이미지를 사용해도 스프라이트 교정·검수 시간을 포함한다.

캔버스·팔레트·파일명·프레임 수는 자동 검사 후보로 두고, 실루엣·광원·문화적 소재·판독성은 사람이 확인한다. 원본과 출처·이용 조건을 기록한다. 캡슐은 작은 크기에서도 제목과 실루엣이 읽히는지 별도로 확인한다.

## 11. 파트타임 운영 방식

- 주 10시간 예시는 평일 2시간 세 번 + 주말 4시간 한 번이다. 생활 일정에 맞추고 한 주에 완료할 기능을 작게 잡는다.
- 매주 마지막 작업 블록에서 빌드·확인·기록을 마친다. 파일 생성만으로 완료 처리하지 않는다.
- 예상시간·실제시간·완료 결과·다음 작업을 기록하고, 작업을 2~4시간 단위로 나눈다.
- 추정이 두 번 연속 크게 빗나가면 남은 시간을 다시 계산한다. 여유 25%를 새 기능에 미리 쓰지 않는다.
- 새 기능에는 코드 시간뿐 아니라 아트 수량·검증 증가도 반영하고, 줄일 범위나 일정 변경을 함께 정한다.
- 시간이 부족하면 장식 애니메이션·사건 수·적 종류·아이템 수를 검토한다. 저장 안정성·조작 판독성·아트 규격은 출시 기준으로 유지한다.

M0~M3에서 엔진 버전, Windows 테스트 경로, 실제 주간 가용 시간, 아트 제작 방식을 확정한다. 첫 20시간 결과로 다음 작업을 재산정한다.

## 12. 모바일 착수 조건

Steam 정식 출시 후 별도 계획으로 산정한다. PC 핵심 재미·안정성 문제가 남으면 먼저 수정한다. 실제 판매와 유지보수 여력, 모바일 요청, 터치 프로토타입에서의 판독·조작 결과를 함께 보고 결정한다. 평가 표본이 부족하면 기간을 연장한다.

착수 시 화면 방향, 큰 보따리 표시, 터치, 발열·배터리, 중단·복귀, iOS/Android 배포, 가격·판매 방식을 검토한다. 모바일 개발과 PC↔모바일 저장 연동 공수는 위 Steam 일정에 포함하지 않는다.
